## Pertanyaan Reflektif

### Tugas 3

1. Jelaskan mengapa kita menggunakan `ModelForm` pada Django alih-alih membuat form HTML secara manual. Selain itu, jelaskan pula mengapa kita diwajibkan menambahkan `{% csrf_token %}` pada form tersebut!

Ans: Kita menggunakan `ModelForm` (`ProjectForm` dan `ExperienceForm` di `forms.py`) karena field form-nya otomatis mengikuti field yang sudah didefinisikan di model `Project` dan `Experience`. Jadi kalau kita tulis manual pakai `<input>` satu-satu di HTML, ktia harus jaga sendiri supaya nama field, tipe data, dan validasinya cocok dengan model, dan itu gampang salah ketik atau ketinggalan update kalau modelnya berubah. Dengan `ModelForm`, validasi seperti field wajib, panjang maksimum `CharField`, atau format `URLField` sudah otomatis ditangani Django dari definisi model, kita tinggal nambah validasi custom kalau perlu (contoh: `clean_image_url` di `ProjectForm` buat nolak link folder Google Drive yang bukan format thumbnail). Manual save-nya juga lebih ringkas, cukup `form.save()`, dibanding kita harus ambil satu-satu `request.POST.get(...)` terus bikin objek modelnya sendiri.

Soal `{% csrf_token %}`, itu wajib karena form kita pakai method `POST` yang mengubah data (create/update/delete). Tanpa token ini, aplikasi rentan kena Cross-Site Request Forgery atau situasi dimana saat website lain diam-diam bikin request POST ke aplikasi kita memakai sesi browser pengguna lain/korban tanpa disadari. `{% csrf_token %}` menyisipkan token rahasia unik per sesi ke dalam form, dan Django bakal menolak request POST yang tidak menyertakan token yang cocok. Karena semua form create project, edit project, create experience, edit experience memodifikasi database, token ini jadi lapisan pertahanan dasar supaya cuma request yang beneran datang dari halaman form kita sendiri yang bisa diproses.

2. Pada Tutorial 03, kita membahas format data JSON dan XML. Mengapa JSON lebih disukai dalam pengembangan aplikasi web modern dibandingkan XML?

Ans: Dari sisi ukuran, JSON jauh lebih ringkas karena tidak perlu closing tag di setiap elemen kayak XML. Bandingkan `{"title": "Golden Hour"}` dengan `<title>Golden Hour</title>`, XML makan lebih banyak karakter untuk data yang sama, dan itu kerasa dampaknya kalau datanya banyak seperti daftar `Project` atau `Experience` di portofolio. JSON juga strukturnya mirip banget sama objek/array di JavaScript, jadi begitu data JSON sampai di browser, dia bisa langsung dipakai tanpa parsing tambahan yang ribet, beda dengan XML yang butuh DOM parser terpisah. Selain itu sintaks JSON lebih sederhana untuk dibaca manusia maupun ditulis manual saat debugging, kita tidak perlu mikirin attribute vs element kayak di XML. Karena alasan-alasan itu, hampir semua REST API modern (termasuk `get_project_json` dan `get_experience_json` yang saya buat) pakai JSON sebagai default, dan XML sekarang lebih sering dipakai di sistem lama atau kasus khusus seperti dokumen dengan skema yang kompleks (misalnya SOAP).

3. Jelaskan alur yang terjadi saat kamu menggunakan fungsi *view* untuk mengembalikan data portofoliomu dalam bentuk JSON. Mengapa kita perlu melakukan proses *serialization* pada model Django sebelum datanya dikembalikan?

Ans: Alurnya dimulai waktu ada request masuk ke endpoint semacam `/api/project/`, yang di `urls.py` diarahkan ke fungsi `get_project_json`. Di dalam fungsi itu saya ambil dulu semua data lewat `Project.objects.all()`, difilter berdasarkan query parameter `title` kalau ada, hasilnya berupa QuerySet yang isinya objek-objek Python model `Project`. Objek model ini tidak bisa langsung dikirim sebagai response HTTP karena browser atau aplikasi lain tidak ngerti struktur objek Python, mereka cuma ngerti teks/byte. Makanya saya panggil `serializers.serialize("json", projects)`, yang mengubah tiap objek `Project` jadi representasi teks JSON (field-fieldnya, termasuk metadata seperti nama model dan primary key). Hasil teks JSON itu baru saya bungkus di `HttpResponse` dengan `content_type="application/json"` supaya klien tahu cara membacanya, lalu dikirim balik sebagai response.

Untuk view yang menampilkan data ke halaman (`show_project` dan `show_experience`), alurnya justru kebalik: saya panggil dulu `get_project_json`/`get_experience_json` buat dapat JSON-nya, lalu deserialize lagi pakai `serializers.deserialize("json", ...)` buat balikin jadi objek model, baru dikirim ke `render()` sebagai context supaya template bisa loop dan akses atribut/method objeknya (seperti `project.get_editing_software_display` atau `experience.is_ongoing`). Serialization dibutuhkan karena format data dan objek Python itu beda, model Django hidup di memori Python dengan tipe data Python (UUID, datetime, dst), sedangkan yang bisa dikirim lewat jaringan atau disimpan sebagai file cuma teks biasa. Serialization jadi jembatan supaya data model bisa jadi format standar seperti JSON yang bisa dipahami sistem lain, dan deserialization adalah proses kebalikannya buat mencairkan teks itu balik jadi objek yang bisa dipakai kode Python lagi.
